# Auditoria de banco, ORM e conexões

**Escopo:** Prompt 04 de `Otmização VPS.md`. Auditoria somente leitura; nenhuma configuração, código, banco, serviço ou dado foi alterado. Nenhum comando foi executado contra o PostgreSQL de produção nesta etapa.

**Data:** 2026-09-24 (America/Sao_Paulo). **Ambiente:** análise estática do checkout local e documentos de auditoria anteriores; sem sessão VPS/SQL. `docs/VPS-OPTIMIZATION-AUDIT.md` contém medições históricas feitas em produção em 2026-09-14, tratadas explicitamente como evidência histórica, não baseline atual.

## Resumo da stack e da evidência

- Backend Java 17 / Spring Boot 3.2.5 / Maven, Spring Data JPA + Hibernate, JDBC PostgreSQL 42.7.3, HikariCP autoconfigurado e Flyway. Evidência: `backend/pom.xml:12,31-52,87-88`; configuração em `backend/src/main/resources/application*.yml`.
- PostgreSQL declarado como `postgres:16-alpine`; migrations Flyway versionadas V1–V53 (53 arquivos). Imagem, versão efetivamente instalada, estado das migrations aplicadas e dados atuais não foram observados.
- Compose declara `shared_buffers=192MB`, `effective_cache_size=768MB`, `max_connections=50`, limite de container 640 MiB; não declara `work_mem`, `statement_timeout`, `lock_timeout` ou limite de CPU. `effective_cache_size` é estimativa do planner, não memória alocada.
- Dois processos Spring configuram pools Hikari: API máximo 8/mínimo idle 2 e scheduler máximo 4/mínimo idle 1. Soma estática: até 12 conexões de aplicação e mínimo nominal 3 se ambos estiverem ativos e as configurações forem aplicadas. Não é medição de sockets, uso, espera ou aplicação efetiva. Outros consumidores do PostgreSQL compartilhado, Flyway, administração e backup permanecem desconhecidos.
- Inventário anterior registra que o PostgreSQL pode ser compartilhado com outras aplicações na VPS. Não se recomenda consolidar bancos/tenants nem reduzir fronteiras de isolamento por conveniência.
