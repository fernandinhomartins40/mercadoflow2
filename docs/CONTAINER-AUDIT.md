**Escopo desta etapa:** auditoria apenas. Nenhum código, configuração, serviço ou dado alterado; nenhum prune, limpeza, DROP/TRUNCATE, restart ou carga em produção executada.  
**Status de cobertura:** `PENDING` = investigação razoável iniciada, mas faltam dados; `AUDITED` = analisado com evidência suficiente no escopo, sem significar corrigido; `BLOCKED` = depende de acesso ou evidência externa indisponível; `NOT APPLICABLE` = inaplicabilidade justificada no fluxo declarado. Métricas ausentes são `NOT MEASURED`.

## Resumo executivo

A stack declarada é Spring Boot/Java 17 + PostgreSQL/JPA/Flyway + React/Vite servido por Nginx + jobs Spring + workers Python, com cliente agente Python para Windows e configurador Electron. O Compose VPS declara oito serviços (um opcional por profile). O inventário e baseline anteriores foram lidos. `docs/VPS-OPTIMIZATION-AUDIT.md` contém observações históricas de produção em 2026-09-14, mas esta sessão não tem shell/SSH na VPS nem métricas ao vivo; aquelas observações não foram tratadas como estado atual.

**Conclusão:** oportunidade de investigação mais forte é custo/semântica do container scheduler e schedulers que também possam iniciar no backend web. Não se recomenda consolidar/remover serviço até reconciliar perfis, tasks reais e locks. PostgreSQL, backend, frontend, proxy, filesystem de imagens/outputs, fila local de agentes e workflows têm consumidores funcionais identificáveis. Redis e MinIO/S3 não são declarados pela stack, mas isso não prova ausência de serviço externo nem cria benefício de removê-los. Não foi encontrado uso do Redis/MinIO no artefato auditado, então a cobertura de integração operacional fica PENDING, não prova de inexistência na VPS.

## Redis, MinIO, painéis administrativos e ferramentas dev

- **Redis:** nenhum serviço Redis em Compose; dependências avaliadas não contêm cliente Redis; caches/rate limiter mostrados são estruturas locais da JVM. Isso não justifica encerrar serviço externo sem acesso ao inventário da VPS. Nenhuma evidência de Redis utilizado para sessões, locks ou URLs assinadas aparece nos arquivos examinados; uso invisível externo permanece PENDING.
- **MinIO/S3:** não declarado no Compose/dependências; armazenamento local claramente atende uploads e arquivos de catálogo/ofertas. Não remover dados nem converter caminhos/URLs durante esta auditoria. Object store seria redesign/migração, não cleanup.
- **Painel super-admin:** aplicação de produto usada por endpoints SuperAdmin, crawler-config/run, manage de catálogo/mercados/planos. Controladores usam `@PreAuthorize` de super-admin e SecurityConfig restringe rotas. Manter o recurso; verificar exposição externa/role e tráfego reais.
- **Ferramentas de desenvolvimento:** Vite dev servers e Electron são scripts de build/dev. Compose local alternativo não é evidência de que esses processos existem na VPS. Não há pgAdmin/Adminer ou DevTools declarados nos manifests pesquisados; processo/porta do host é BLOCKED.
- **Sessões, rate limiting, locks e cache:** pareamento armazena sessões no banco e expira via scheduler; rate limit Bucket4j em memória; outros caches em memória; fila do agente no cliente usa SQLAlchemy e persistência local. Não existe evidência suficiente para trocar/remover qualquer uma dessas funcionalidades. Locks/advisory/distributed scheduler locks não foram confirmados.
- **Signed URLs e consumidores externos:** solução encontrada serve links locais da aplicação, sem S3 presigning identificado. Browsers, agentes, collectors, Stripe, fornecedores varejistas e workflow GitHub são consumers externos comprovados pelo código/workflows; quem consome outputs de ofertas e tráfego real precisa observação de acesso.

## Achados sem recomendação de remoção

1. CTR-04 não é “cron redundante” até que todos os `@Scheduled` estejam atribuídos a perfis e haja exclusividade/lock verificado. Há risco possível de scheduler em backend e jobs, mas estado runtime e efeito são NOT MEASURED.
2. Harvester e barcode podem ter períodos ociosos entre execuções, mas usam loop persistente configurável, checkpoint/API e consumidores de dados; execução sob demanda tem risco de freshness e operação.
3. Dois Nginx têm funções distintas (static root e API reverse proxy); a duplicação de processo não é critério suficiente para remover um deles.
4. PostgreSQL é a fonte de estado durável e contém migrations, policies RLS, seeds, pareamento, crawler runs/checkpoints, cache persistente de resultados e estado comercial. Nenhuma consolidação com banco de clientes é proposta.
5. Redis não está declarado, logo não existe serviço de Compose a classificar como “ocioso” neste repositório. A hipótese de serviço externo ficou sem cobertura de runtime.
6. MinIO/S3 também não está declarado, mas o filesystem local é consumidor funcional de imagens e renders. A hipótese de “trocar storage para baixar containers” não se aplica ao estado declarado e exigiria migração de URLs/dados.
